## Architecture audit

- The application uses React and Next.js App Router conventions compiled by
  Vinext into a Cloudflare Worker. `worker/index.ts` is the Worker entry point;
  `app/api/**/route.ts` supplies server routes.
- Runtime bindings are read from Cloudflare's Worker environment. D1 is bound
  as `DB`; R2 is bound as `BUCKET`.
- The repository already used Drizzle schema/migration files for D1, while the
  character routes used raw prepared D1 statements. Phase 4B retains that
  pattern: Better Auth uses its native D1 support, its schema was generated by
  the official CLI, and application queries stay explicit prepared SQL.
- The existing `characters` table uses a random text internal primary key and a
  JSON `data` document plus summary columns and optimistic `version`. Existing
  records were globally listed and write routes did not have account ownership.
  Some browser-only character state also remains for the non-cloud root sheet.
- Existing create/load/update/delete routes live under `/api/characters`.
  Import/export were client-side JSON operations; they are now authenticated
  server operations. Client-supplied JSON is recursively stripped of ownership,
  account, email, session, and token fields.
- Portraits were already stored in R2 and referenced in character JSON. Phase
  4B makes the character-to-object key server-controlled, enforces the same
  visibility rules during retrieval, and restricts upload/replace/delete to the
  owner.
- No existing table names conflict with Better Auth's generated `user`,
  `session`, `account`, `verification`, or `rate_limit` tables.

## Authorization and security review

- Better Auth is mounted at `/api/auth/*`, uses native D1 storage and secure
  cookie sessions, and is configured only for Google (`openid`, `email`, and
  `profile`). Email/password and cross-subdomain cookies are disabled; CSRF and
  origin checks remain enabled.
- The trusted production origin is exactly `https://taleswithoutend.com`.
  Only the actual local port at `localhost` and `127.0.0.1` is additionally
  trusted. Fallback-Worker auth actions redirect to the canonical origin.
- Owners are derived exclusively from the validated session. Client ownership,
  public IDs, visibility, account, email, and token fields are discarded.
- Private reads are hidden with 404. Other users receive 403 on attempted
  writes to public/unlisted characters. Missing authentication receives 401.
- Public IDs use 16 cryptographically secure bytes (128 bits), base64url
  encoded with a `chr_` type prefix and protected by a unique index. Creation
  retries collisions. Names and account data never affect IDs.
- New/imported records are private. Imports support v1, v2, and legacy bare
  JSON but always receive a fresh server ID and the current session owner.
- Exports are owner-only and strip all account/session/claim data plus internal
  portrait URLs.
- Portrait object keys include only the opaque public character ID and a random
  UUID. Uploads are limited to 5 MB; JPG, PNG, WebP, and GIF content types must
  match file signatures. Retrieval rechecks character privacy. A normal save
  cannot replace the server-controlled portrait reference.
- Claim tokens contain 256 random bits. Only SHA-256 hashes are stored. Claims
  are expiring, revocable before use, session-required, and conditionally
  assigned through a D1 batch so only one claimant can succeed.
- Request JSON is streamed with explicit size bounds. D1 values use prepared
  bindings in application routes.
- No secret values are committed, serialized, logged, or required during the
  production build.

## Migration execution and recovery plan

1. Keep this branch unmerged until code, SQL, and authorization review are
   approved.
2. Immediately before migration, confirm the remote target reports database ID
   `8e2bf197-e20f-4ea7-a86f-cab4e1a74699` and list the exact pending files.
3. Confirm D1 Time Travel is available for a restore point immediately before
   applying the reviewed pending set (`0001`–`0004`).
4. Apply the migrations deliberately; deployment does not run them.
5. Verify existing row counts and a sample of legacy JSON/revision records
   before any backfill.
6. Run the public-ID backfill first as a dry run. Apply it only after reviewing
   the selected production target and record count.
7. Generate claims only for explicitly selected records.

If schema migration fails, D1 rolls back the failing migration. If a successful
migration or later backfill must be recovered, restore the production database
to the pre-change Time Travel bookmark, redeploy the previously approved main
commit, and investigate on a separate branch. Do not attempt an ad-hoc reverse
schema migration that could discard auth or character data. R2 objects are not
renamed or rewritten by the schema migration or public-ID backfill.

## Production verification checklist

Perform only after approval, merge, deliberate production migration, and
public-ID backfill. Use disposable test records; do not run destructive preview
tests if a branch preview is attached to production `DB` or `BUCKET`.

1. Open `https://taleswithoutend.com`.
2. Sign in with an authorized Google test account.
3. Confirm the callback returns to the root domain.
4. Confirm the signed-in session survives refresh.
5. Create a temporary private test character.
6. Confirm its URL contains only an opaque character ID.
7. Confirm it remains available after refresh.
8. Open its URL signed out and confirm it is unavailable.
9. Change it to unlisted.
10. Open its URL signed out and confirm it is viewable but not editable.
11. Confirm it does not appear in the public library.
12. Change it to public.
13. Confirm it appears publicly.
14. Sign in with a second test account and confirm it cannot edit.
15. Sign out and confirm edit controls disappear.
16. Test one portrait upload and retrieval.
17. Delete the temporary test character and confirm its URL no longer works.
18. Claim one selected legacy test character using the one-time claim process.
19. Confirm the claim token cannot be reused.
20. Confirm Cecil and every other legacy record remain unchanged unless
    explicitly selected.
